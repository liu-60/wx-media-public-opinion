# 配置管理中心：详细业务与技术规格

> 本文是未来开发的目标规格。文中“应/必须/新增”不代表当前已有；现状以 01 的核验清单和当前代码为准。不得把设计中的 API/DTO 当成数据库字段。

## A. 全局界面与交互

### A1. 信息架构

固定左侧导航宽 220px，顶部工具栏高 60px，主内容水平内边距 24px。五个一级入口：账号管理、文章管理、过滤规则、热词管理、采集策略。默认进入账号管理；每页保留独立筛选状态。沿用现有 `view` URL 参数，不另引入路由框架。

顶部仅显示当前模块、真实连接状态、刷新按钮。首次加载先显示页面壳和当前模块；六表计数为延迟信息，不阻塞列表。不新增大屏、营销卡片、二级菜单、无关用户系统或报表模块。

页面结构统一：标题与简短说明 → 高频筛选 → 可折叠更多筛选 → 已选条件 Tag → 选中记录批量工具条 → 数据区 → 分页。规则使用分组配置区，策略使用卡片区，可复用同一组加载/错误/空态和表单能力，不强制所有模块变成表格。

### A2. 视觉参数

| Token | 值/要求 |
|---|---|
| 页面/卡片 | `#F6F7FB` / `#FFFFFF` |
| 主/次文字 | `#1F2430` / `#6B7280` |
| 边框 | `#E8EAF0` |
| 主色/浅主色 | `#635BFF` / `#F0EFFF` |
| 间距/圆角 | 卡片间距 16px，圆角 12px |
| 表格 | 行高 48px，表头 44px，数字右对齐、标题左对齐 |
| 文本 | 系统中文字体；正文 14px，辅助 12px，页标题 22px |
| 通过/过滤/待处理/自动/警告 | 绿/红/灰/蓝/橙，均带文字，不只靠颜色 |
| hover | 140ms |
| Drawer/Popover/筛选展开 | 220ms / 160ms / 200ms |

使用 opacity、transform、background-color；禁止大渐变、重阴影、弹跳、持续动画。支持 `prefers-reduced-motion`。列表只在结果首次未知时显示骨架；已有结果刷新时保留旧行并显示轻量加载标识。

屏幕 >=1200px 固定侧栏；768–1199px 可收窄侧栏；<768px 改折叠菜单，抽屉全宽。表格允许自身横向滚动，不能给 body 设置 960px 最小宽度撑破屏幕。固定表头和末尾操作列，正确处理背景/z-index，避免覆盖滚动条。

### A3. 公共能力与事件

在当前原生 JS 中实现轻量函数/配置，不强制创建组件框架：

- `DataTable`：列定义、行 key、格式化、选择、固定头/操作列、加载/空/错误、分页和排序回调；不包含业务查询。
- `FilterBar`：query object、基础/更多条件、单个移除/全部清空、搜索 debounce、URL 同步。
- `StatusTag`、`MetricValue`：只负责展示，null/undefined 显示 `—`，0 显示 `0`。
- `EditDrawer`：打开后按需请求、取消旧详情请求、脏表单确认、保存状态、字段错误、冲突展示。
- `ConfirmDialog`：显示操作对象、数量、后果、提交中状态，删除不通过普通 toast 直接完成。

普通 DOM 生命周期共用一个根事件委托；避免重新渲染时叠加监听。选中行变化仅更新行/选择计数，不重建整个筛选表单。输入中文时 `compositionstart` 到 `compositionend` 之间不发送查询，结束后再 debounce。

Drawer：打开时记住触发按钮；焦点进入标题或第一个控件，Tab 保持在抽屉内，Escape 按关闭规则处理，关闭后返回触发位置。保存失败保留草稿；保存中禁用重复提交。取消请求不等于撤销已经提交的服务器写入。

## B. 查询、缓存与公共 API 规范

### B1. 保留现有响应外壳

列表继续返回 `{items,total,page,pageSize}`，详情继续 `{item}`，新增成功 201，其余成功通常 200。策略当前只有 `{items}`，扩展分页时保留 items 并补足分页元数据。不要改成全新 `{code,data,message}` 破坏现有前端。

内部 Supabase client 的 `{data,total,status}` 只在 service 使用，不能与 HTTP 列表契约混淆。`total` 缺失必须表示未知（null）；不能用当前页长度冒充总数。未知总数显示“已加载 N 条”，通过多取一条或可靠的下一页信号决定是否可翻页。

错误保留 `{error:string}` 兼容，可增量增加 `{code,details}`，不移除 error。使用简洁中文给用户，内部日志脱敏：400 输入错误；401 本机令牌无效；403 来源不允许；404 不存在；409 冲突/部分写入；413 请求过大；415 非 JSON；421 Host 不允许；502 上游失败；503 未配置/能力不可用。未知字段不要整包透传数据库。

`details` 可以携带本次失败字段、失败 ID、实际成功数，不包含密钥、Cookie、SQL 原文或全部底层响应。0 行更新/删除不是成功：区分目标不存在、版本冲突、权限不足；不要一律补发无条件写请求。

### B2. 分页、筛选、排序

- 页码从 1 开始，默认 pageSize=50，允许 20/50/100。`offset=(page-1)*pageSize`。若使用 Supabase SDK，range 两端均包含，结束位置为 `offset+pageSize-1`。[官方 range 说明](https://supabase.com/docs/reference/javascript/range)
- 列表使用服务端搜索/过滤/排序，禁止下载万条账号/文章后在浏览器筛选。
- 更换筛选、排序、页大小后 page=1；删除末页全部记录后回到最后有效页。保留用户其他筛选。
- 每次排序追加稳定主键：账号 `account_id`；文章/热词/规则 `id`。明确 null 排序，不把 null 当最小数字后在客户端补排序。
- 参数名称、字段、运算符均用白名单；构造 PostgREST 条件集中于 service，不直接拼入用户输入。使用 URLSearchParams 正确编码 `wx_biz` 中的 `+`、`/`、`=`，不得破坏精确身份字符串。
- 下限独立、上限独立、两者并存均有效。`0` 是有效输入；空值才表示不筛选；NaN/Infinity/负值/上限小于下限在网络调用前返回 400。
- 关联字段筛选必须影响父记录集合。账号不带画像筛选时使用左关联，保留无画像账号；带地区/类型/活跃度筛选时使用 `account_profiles!inner` 或等价经验证的服务端查询，不能先分页账号再在浏览器过滤画像。
- 首屏按有限字段投影。允许为一页账号关联必要画像字段，不等于禁止 JOIN；禁止拉取整份画像供首屏使用。不能逐行发 N 次详情请求。

具体PostgREST条件参考（已从当前service的无网络查询捕获核对）：账号阅读区间使用 `and=(read_median.gte.10000,read_median.lte.100000)`；画像活跃范围使用 `account_profiles.and=(active_days.gte.5,active_days.lte.20)`，与`account_profiles!inner`配合。若单字段直接赋值，键为read_median时值应为`gte.10000`，不能再写`read_median.gte.10000`。沿用当前setAndConditions扩展，不能在五页各自拼另一套。

### B3. 时间与数值口径

本项目当前查询采用 UTC。为避免静默改变已有结果，本包默认保留 UTC 日界并让展示、筛选标签、日期说明明确标注 UTC。不要用操作系统时区替代业务时区。若用户明确改为中国自然日，集中修改业务时区常量及转换，补 UTC+08:00 边界回归，不能只改格式化函数。

时间区间采用 `[开始日 00:00, 结束日次日 00:00)`，拒绝不存在日期，如 2026-02-30。`stat_date` 和策略 `date` 是纯日期，不因时区转换前移一天。月份显示 `YYYY-MM`，存储 `YYYYMM`，例如 `2026-09 → 202609`。

只读统计值不主动修正数据库。bigint ID 当前可用正安全整数，入口必须检查 Number.isSafeInteger；遇到超界值不得四舍五入，应报告兼容性缺口或统一改用无损字符串链路。普通 int4 非负范围不能超过 2147483647；策略 cursor 与热词计数要检查 int2 上限 32767。

### B4. 请求与缓存

搜索 debounce 400ms；Enter 可立即提交。select/change 每次只触发一次查询。AbortController + requestId 双重保护：旧请求即使完成也不能覆盖新查询结果；Drawer A 关闭后其结果不能填入 Drawer B。

继续扩展已有 GET 缓存/in-flight 去重；key 包括模块、规范化筛选、页码、页大小、排序。建议列表 TTL=30s、详情=15s、summary=60s；这些是实现默认值，可在一个位置调整。缓存容量默认 100 个 key，过期或淘汰后清理，不无限增长。

每个资源维护缓存代际。缓存和in-flight均记录代际，只有同key且同代际才能复用promise。写成功后失效相关key并推进代际，允许启动新代际GET；旧GET既不能写缓存，也不能被新代际刷新复用或交付结果。旧promise的finally只能清理仍指向自己的登记项，不能删除新请求。不要在同代际为重新查询直接删除仍执行的inFlight引用制造重复请求。

状态/标签变化：刷新对应账号行/详情及受筛选影响的当前页，不刷新六表总量。删除文章：失效文章列表/详情和文章计数。规则增删：失效规则组/列表及规则计数；仅启停不影响总条数。热词合并：失效参与项、列表及热词计数。策略改配置：失效策略列表/详情，不重数其他五表。

写操作默认不自动重试；尤其超时后应先读回实际状态，防止重复插入、合并或删除。GET 可有限重试，退避且尊重取消；不能无限轮询。

## C. 账号管理

### C1. 列表字段与来源

| 中文列 | 数据来源 | 处理 |
|---|---|---|
| 公众号名称 | accounts.wx_name | 次行可显示 wx_biz，名称缺失显示“未命名账号” |
| 认证主体 | accounts.verify | 文本，不凭空转为 boolean 认证状态 |
| 类型/地区 | account_profiles.wx_type/region | 无画像显示 — |
| 平均阅读 | account_profiles.read_avg | 只读 |
| 中位/最高阅读 | accounts.read_median/read_max | 与筛选排序保持同源 |
| 活跃天数 | account_profiles.active_days | 不自行换算活跃百分比 |
| 审核状态 | accounts.decision_status | 0待审核、1通过、2过滤、3待复核；null显示“未标注” |
| 决策来源 | accounts.decision_source | manual人工、auto自动、null未标注；不是账号采集来源 |
| 更新时间 | accounts.updated_at | 沿用既有采集更新时间策略 |

所有同名字段禁止对象展开覆盖。profile.read_median/read_max 如需比较，使用 `profile_read_median/profile_read_max` DTO 别名并仅在详情展示。

高频筛选：名称/wx_biz、审核状态、类型、地区。更多筛选：中位阅读最小/最大、活跃天数最小/最大、更新时间起止、决策来源。现有参数继续 `keyword,status,wxType,region,minRead,maxRead,minActive,maxActive,sort,page,pageSize`；新增明确为 `updatedStartDate,updatedEndDate,decisionSource`，在 service 实现，不是 UI 自行筛选。

允许当前实际支持的排序 `account_id,wx_name,read_median,read_max,updated_at`。平均阅读/活跃天数若无法用当前 REST 关联排序经真实查询验证，不给可点击排序箭头；不能对当前页排序冒充全局排序。

### C2. 详情抽屉

宽度建议 720px。分区：身份与简介、采集画像、阅读/互动指标、人工配置。打开后按 account_id 单独加载完整 profile；列表只用必要画像字段。若账号存在但画像缺失，显示“暂无采集画像”，账号仍可审核。

完整画像按 04 中真实字段展示：头像、微信号、类型、地区、自动标签、最近发文、文章量/活跃、阅读/在看/点赞/分享/评论的均值中位最大、爆文数量/比率、原创数量、采集时间。统计字段全部只读。burst_rate 的百分比含义没有数据注释保证时保持原值，不能直接乘100并称为百分比。

唯一人工输入：decision_status 和 manual_tags。manual_tags 用 Tag 输入，trim/去空/精确去重，中文逗号、英文逗号、换行可作为输入分隔，确认后为字符串数组；默认 UI 最多50个、每项50字符，这是表单容量规则，不是数据库约束。现有异常 JSON 不自动覆盖为空，先只读展示并报告。

### C3. 保存、并发与批量

只提交已改变字段。标签未变不发送 manual_tags；状态未变不发送 decision_status。修改状态时服务端同时写 `decision_source='manual'`、`filter_rule_id=null`，符合现有 CHECK。仅改标签不能触碰状态、来源、规则引用和采集统计。

账号 updated_at 目前没有 UPDATE 触发器，且含采集时间语义：不能为了并发检测把它当人工编辑版本，更不能改 collected_at。状态提交增加 `expected_decision`（仅请求元数据），包含抽屉打开时的 status/source/filter_rule_id；服务端以主键+旧三元组作为同一个 PATCH 条件，必要时再带既有 updated_at。null 使用正确 is-null 条件，不能 eq.null。

标签提交增加 `expected_manual_tags`；针对 profile 主键和原 JSON 值做条件更新。profile 原本不存在时只插 `{account_id,manual_tags}`；若发生唯一键冲突重新读回并报告冲突，不覆盖另一方的新标签。原有 profile 存在但条件更新0行不能误判“画像不存在”并尝试插入。

所有jsonb/text[]旧值条件共用一个序列化入口，并验证真实REST支持。覆盖SQL NULL、JSON null、空数组、中文、引号、逗号、反斜杠、数组顺序；不得将JSON包含运算当成完整相等。现client把条件编码进URL，需测量最终URL的UTF-8字节数和1MB请求体上限；大快照超过已验证传输边界时返回明确能力限制，不截断数组、不降级为无条件PATCH。不能因1000个目标被表单接受，就推断可将全部旧对象放进任意长度URL；必要时只保护真正参与变更和校验的字段，并如实记录有限保护边界。

两项一起保存涉及两表：现有 REST 不提供跨请求事务。明确状态成功、标签失败、补偿成功/失败/结果未知。补偿只能匹配本次写入后的状态，不能无条件恢复旧行覆盖别人修改。若网络超时，先读回再判断，不盲目回滚。失败时保留用户草稿，展示已保存与未保存字段。

批量状态支持通过、过滤、待审核、待复核。默认只选择当前页；换页/筛选清除选择并提示，不实现“全库全选”。批量最大100条，每行携带 expected_decision；服务器受控并发不超过5，不长时间阻塞 UI。保留 `{count,requestedCount}`，增加 `{succeededIds,failed:[{id,code,message}]}`；count必须等于实际成功记录数。成功项从选择中移除，失败项保留，可只重试失败项。

不同保存请求只改其白名单字段，统计同步不应读出人工值再回填旧值，应完全不提交人工字段。账号删除不在本次需求中，不新增删除按钮。

## D. 文章管理

### D1. 展示与筛选

列：标题、公众号、发布时间、阅读、点赞、在看、分享、评论、原创状态。真实字段为 `title,publisher,published_at,read_num,like_num,look_num,share_num,comment_num,is_original`；publisher来自accounts.wx_name。标题单元格不默认展示 article_sn 等技术内容。

原创 boolean三态：true原创、false非原创、null未知；筛选支持全部/原创/非原创/未知，不能用 Boolean(null) 抹掉未知。`read_num_capped=true` 表示截断读数；以“≥实际保存值”显示，可在 100000 时显示“10万+”，不得声称精确值。

高频筛选：标题 keyword、公众号远程搜索选择 accountId、发布时间范围。更多：阅读/点赞/分享/评论最小最大、原创状态；在看至少展示和排序，可扩展范围但不必新增业务需求。

保留现有 `read_numMin,like_numMin,share_numMin,comment_numMin`，增加对应 `...Max`；新增 `isOriginal=true|false|unknown`。保留 `publisher` 模糊名称查询，精确账号选择优先 accountId，同名公众号不能混为一项。已有 sort白名单为 published_at/read_num/like_num/look_num/share_num/comment_num/id；排序在服务端完成。

详情按需 GET `/api/articles/:id`。仅真实字段，不能伪造文章正文、摘要、情感分析等库中没有的数据。技术信息收进“技术信息”折叠区：id、account_id、article_sn、idx、source_code、updated_at；source_code没有映射依据时显示数字，不编来源名称。

### D2. 打开与删除

主操作“打开原文”，次操作“详情”，删除收进更多菜单。原文链接只允许 http/https，缺失时禁用；新窗口使用 noopener/noreferrer。所有数据库文本通过安全文本渲染/转义，不能插入未转义 HTML。

单个/批量删除使用现有 DELETE `/api/articles` 和 ids。确认框显示选中数量与最多3篇标题、不可撤销、仅当前选择范围。删除前不自动导出整个库。可在请求加逐项快照信息保护并发，成功后按真实返回 ID 更新界面。

文章的 `(account_id,article_sn)` 唯一键不能改成标题唯一。数据库在插入时按 `published_at DESC,id DESC` 保留每账号最近20篇：列表显示的是当前留存文章，不是公众号历史全量；不得因列表少于上游数量判断丢失，也不得删除该触发器。

删除文章不会自动清理 hotwords.article_keys，因为它没有外键且可能指向外部平台。保留现有语义，不在删除接口扩展跨表业务；在帮助说明中说明热词来源计数与当前文章留存数可能不同。

## E. 过滤规则

### E1. 真实字段字典

| 作用域 | UI字段 | filter_rules.field_name | 业务记录字段 |
|---|---|---|---|
| account | 公众号名称 | name | accounts.wx_name |
| account | 认证主体 | verification | accounts.verify |
| account | 简介 | description | accounts.description |
| account | 中位阅读 | read_median | accounts.read_median |
| article | 标题 | title | articles.title |
| article | 阅读 | read_count | articles.read_num |
| article | 点赞 | like_count | articles.like_num |
| article | 评论 | comment_count | articles.comment_num |

不能往 field_name 写 wx_name、verify、read_num。数据库没有分享/在看规则字段，不能因为文章列表有这些列就给规则表新增选项。

文本只开放 contains（包含）、not_contains（不包含）、eq（等于）；数值只开放 eq/gt/gte/lt/lte。命中规则表示过滤，不是通过条件。例如 `read_count gt 6000` 表示大于6000时过滤；不要因觉得反常擅自反转。

contains/not_contains只能 value_text 非空、value_number=null；比较数值只能 value_text=null、value_number是有效数；eq 按字段类型选一列。编辑改变字段/运算符时清理另一类值，不能留下两列都有值。enabled必须是真boolean，不能把字符串"false"转换为true。remark最大255字符；hit_count/created_at/id是只读。

### E2. 关键词分组与差量保存

默认展示名称、认证、简介三个账号关键词卡片，以及文章标题关键词卡片；其余数值规则表列“作用域、字段、运算符、阈值、启用、存量命中数、操作”。关键词以Tag编辑，不展示100多条重复表格行。

不能在100条分页结果上分组后声称完整。新增轻量 GET `/api/rules/groups`：服务端按固定排序分页读齐当前小型配置集，只取需要列，在server完成分组；默认安全上限5000行，超出明确返回容量错误，绝不静默截断或删除未读到的行。此特殊处理仅适用于小型规则配置，不适用于账号/文章。

分组键为 `(scope,field_name,operator)`，不能将 contains与not_contains合并。每个Tag保留原始 `id,enabled,remark,hit_count,updated_at`；同组混合启停显示每项状态。group启用状态三态：全启用/全停用/混合。分组命中数是规则 hit_count 之和，标注可能重复计数，不能称为唯一账号数。

唯一转换入口建议在现 service 扩展 `buildRuleGroupDiff(originalRows,draft)`：返回 insert/update/delete/unchanged四类，每类保留真实ID。未修改行不写回，不重置hit_count，不删除后重建全部规则。新增关键词trim/去空/精确去重；不默认简繁转换或模糊合词。保留同字在不同字段/运算符中的独立规则。

保存可新增 POST `/api/rules/groups/save`，这是目标接口并非现有。请求携带 groupKey、原始行快照和明确变更。服务器重新校验归属，禁止操作其他组ID；执行唯一diff函数并返回逐项结果与最新组。删除候选只能来自用户打开时的原始ID；每个update/delete以id+groupKey+原updated_at为同一请求条件，0行返回冲突。不能拿重读到的最新整组重新算删除集合；其他人后来新增的Tag必须保留。分组写不具备事务，失败返回部分结果，不能把新草稿整体当成功替换；重试只提交尚未成功且重新核对的操作。

规则唯一索引分别为 `(scope,field_name,operator,value_text)` 和相同前三列+value_number，且仅对应值非null生效。重复插入应返回清晰409或识别为已有相同规则，不要删除原行丢失ID/历史计数。

删除规则会使 accounts.filter_rule_id 按FK自动设null，但不会自动重新判定账号decision_status。删除确认说明此后果；停用更适合保留历史关联。删除或停用都不重跑历史数据。

### E3. 保存后真正生效的规则链路

复用 `src/article-filter.mjs` 的持久规则解释器与 `run-pipeline --rules-from-supabase`；在线模式的同一次运行启动时读取启用规则，按稳定ID顺序固定快照，持久化报告中的 `{source,loadedAt,count,hash}`。现状只在stdout打印部分元数据，需要补写报告。读取失败或出现不支持的字段/运算符应明确失败，不静默回退默认规则或悄悄忽略。

空规则数组是有效配置，表示不应用持久规则，不与离线默认规则叠加。离线default.json模式保留，界面/报告明确来源，不能把离线结果标成数据库规则结果。

执行顺序：解析并统一文章/账号输入 → 获取当前账号决策 → 已过滤账号阻断 → 账号规则 → 文章规则 → 现有内容有效性检查 → 输出判定 → 按同一身份建立远端写集合。

本包明确的保守默认：`decision_status=2` 的账号始终阻断；人工通过是人工维护的审核标记，本次不新增“豁免所有自动规则”的能力。自动执行不得覆盖人工状态；仍命中规则时报告实际过滤原因，不把人工状态回写成自动。若产品确实要“人工通过豁免账号规则”，先由用户明确该业务变更，不能弱模型自行增加白名单豁免。

Supabase当前决策必须通过现有server-side查询按输入wx_biz分批读取，送入原判定入口；只修改coarseFilterArticle而没有供给真实决策不算接通。不要给本地SQLite加一套新人工决策权威库。

数值规则：null/undefined/空字符串/全空白跳过，真实0正常比较；非有限值拒绝或明确记数据无效，不能默认0。文本字段为null时跳过匹配，包括not_contains；真实空字符串如何处理与既有标准化保持一致并以回归锁定。所有规则共用一个比较器。

统一 `pipeline` 与 `supabase-sink` 当前两处文章标准化：同一输入的显式ID、article_sn、URL sn、fallback key必须得出同一个判定关联键；保留远端真实唯一约束 `(account_id,article_sn)`。补齐commentNum/comment别名；没有判定结果的文章不得默认远端放行，应记录为待核对/阻断且不写入。不要通过粗暴将所有缺ID文章丢弃来掩盖标准化错误。

hit_count目前缺少可验证的统一写回链路，页面按数据库现存值只读展示，不声称实时命中数；本次不新增计数任务或修改数据库。规则保存成功文案：“配置已保存；使用数据库规则的下一次执行将读取新配置”。

## F. 热词管理

### F1. 页面与编辑

列表：标准词hotword、aliases、stat_date、article_count、代表文章article_url。支持按statDate和标准词搜索；不引入前端全表搜索。保留现有service。

编辑Drawer仅允许标准词与aliases；现有article_url编辑能力可保留在高级区域，URL必须合法。日期、计数、article_keys只读；标准词trim后1–50字符；aliases为string[]。别名去空去重，不将标准词重复放入别名。

没有hotwords.updated_at/version，不能照搬账号的expected_updated_at。编辑请求携带expected_snapshot；服务端至少重新读回并对比，再用已核验可支持的旧值条件更新以缩小窗口。UI版本检查不是事务；必须保留当前并发限制说明。改名与同日已有词撞唯一键时显示409，并引导用户选择现有合并入口，不自动删除冲突行。

单条删除保留在更多菜单：确认显示标准词和日期，说明仅删该热词记录、不删来源文章；取消确认不发写请求。提交旧快照，变更/0行返回冲突或不存在，失败保留列表。成功后读回确认记录不存在，只刷新热词列表/计数，末页为空时回到最后有效页。删除不作为重复词冲突的自动修复方式。

### F2. 合并步骤必须固定

1. 选择2–100条当前可见热词；只允许相同stat_date。跨日期时显示原因并禁止提交。
2. 打开合并确认，用户从所选项中明确选目标标准词；不能隐藏地选最小id或当前排序第一条。
3. 服务端重读选中行，校验全部存在，目标ID属于所选集合；可新增 `/api/hotwords/merge-preview` 返回只读预览和当前快照，不在前端再实现合并算法。
4. 复用 `canonicalHotwordMerge → mergeHotwordRow`：保留目标id/标准词/日期；来源标准词加入aliases；aliases与article_keys各自精确去重；count重算为唯一key数；保留目标有效代表URL，否则取确定的第一条有效来源URL。
5. 预览展示保留项、删除项、合并后别名、唯一文章数和日期。`article_count`须在2–32767，越界明确拒绝，禁止截断数组或把计数裁剪后保存。
6. 用户确认后POST现有 `/api/hotwords/merge`，必须显式 `target_id`，并新增expected_snapshots保护本次预览。不可让旧客户端省略目标时静默挑选；前后端同步收紧校验。
7. 成功后读回目标、确认来源确已删除，返回真实 `{targetId,removedIds,row}`；清选择、失效相关缓存。

所有article_keys是不透明来源键，可包含`tophub:<id>`、URL或其他业务key，不得当作articles.id外键，不得遍历所有keys逐条请求文章。

### F3. 非原子写与快照语义

当前没有业务事务RPC，不新增数据库函数。合并多个REST请求不是原子操作，使用进程内同热词ID互斥只能减少本进程重复请求，不能阻止外部采集器。

实现原则：先读取与验证快照；目标条件更新；来源条件删除；核对实际影响行和终态。发生错误/超时先读回参与行：若所有来源还在且目标仍等于本次写入结果，可有条件恢复目标；若部分来源已删除或他人已更新目标，不能盲目回滚目标丢失来源数据，应返回明确部分结果与人工核对信息，保留证据。禁止自动无限重试合并。若产品要求严格全有或全无，本约束下尚未满足，报告必须已有事务入口或另行批准的方案，不能包装补偿成事务。

区分三种已有语义：

- 手工合并不同热词：并集去重，保留指定标准词。
- 普通采集upsert同日同词：沿用普通合并逻辑。
- TopHub `replaceExisting:true`：对本次输入存在的同日同词替换aliases/keys/count，不保留旧snapshot keys；它不是“删除当天所有未出现热词”。

TopHub仍按每个规范平台仅保留第一条来源。不要把这条规则误改为手工合并时只保留一个平台，也不重新写TopHub聚类算法。

## G. 采集策略

### G1. 卡片与字段边界

每张卡片标题由类型与ID派生，如“账号策略 #1”，不新增name列。展示：request_type、source_targets数量、active_targets数量、completed_items条目数、date/month、中位无关的min_read/max_read范围、cursor、cycle_no、预计请求量。没有确认completed_items元素结构时只显示数组长度，不猜文章总数或百分比。

明确cursor含义：0=未激活；1=请求1页、不翻页；2=请求2页；N=最多配置N页。它不是WxRank返回的next_cursor，不表示正在运行/暂停/已完成。显示“配置未激活/已配置N页”，运行状态必须来自真实执行器。

`expected_requests = active_targets.length × cursor`，只说明目标×页数的配置估算，不承诺实际调用数、费用或剩余额度。重试、分页提前结束和平台限制都会使实际值不同。没有任务进度数据时不显示伪造进度条。

### G2. 编辑表单

普通表单：类型、来源目标、当前启用目标、时间条件、阅读上下限、请求页数。completed_items/cycle_no是执行进度数据，默认只读；不因保存其他设置清空。原有高级JSON入口可以保留为只读诊断，不能提供绕过类型校验的任意JSON写入。

| request_type | 来源/启用目标控件 | 时间条件 |
|---|---|---|
| account | 远程搜索账号多选，名称+wx_biz区分，source与active分别选择 | 可无时间，也可date或month二选一，依据执行器支持状态提示 |
| keyword | Tag，trim去重，启用项只能来自来源项 | 可无时间，也可date或month二选一 |
| wx_type | 实际24分类多选，启用项是来源子集 | 可无时间，也可date或month二选一 |
| date | 日期控件，不显示任意账号Tag | date必填，month=null；targets编码须来自已核验runner合约 |
| month | 月份控件 | month必填，date=null；targets编码须来自已核验runner合约 |

实际24分类已从真实策略记录核验：时事、文化、健康、职场、学术、美食、民生、科技、情感、楼市、汽车、幽默、政务、财富、旅行、企业、时尚、美体、教育、体娱、百科、乐活、创业、文摘。作为集中常量复用；不是数据库 enum。不要用模型记忆换成其他平台类别。

account目标当前真实形状：`{account_id,wx_biz,wx_name,read_avg}`。新选择从服务器返回的真实账号构建最小对象，wx_biz为去重身份，account_id必须与其匹配；wx_name/read_avg只是当时显示快照，不当身份依据。已有合法对象中的未知扩展字段保持原样，不能把整份profile塞进新目标对象。

keyword与wx_type目标为字符串数组。active以wx_biz或精确字符串匹配，必须是source子集；重复目标只计算一次。删除source中已启用对象要在草稿预览中说明active也会移除，用户一次保存确认，不自动改completed历史。

date/month类型当前无真实记录样本，库只约束JSON类型，无法确定runner期望的targets结构。允许保存明确标为“仅配置”的date/month参数，默认保留原targets；新建时source/active初始化[]、cursor=0。执行器未核验前不得自动填入虚构目标把预计请求数凑成1，不能激活执行或声称可采集。这是明确能力缺口，不是留给模型自由发挥。

### G3. 校验、生命周期、保存

cursor为0–32767整数，cycle_no为1–2147483647整数；阅读值为空或0–2147483647整数，min<=max；真实日期校验，month严格YYYYMM有效月份；date/month不可同时非null。PATCH必须合并当前行验证完整结果，不能只验证用户传入的半边范围。

目标数量默认单组最多1000，超限返回明确提示；此为应用容量保护，不改库约束。新建时id/updated_at交给数据库默认，cycle_no=1、completed_items=[]。保存配置不增加cycle_no，不重置进度，不触发采集。已有策略修改request_type可能改变targets结构：默认不允许就地切换类型，提示新建该类型策略；新建Drawer切换类型时清除不兼容草稿并提示。

策略updated_at只有插入默认值，没有UPDATE trigger。服务端在每次配置修改中显式写入新的更新时间，并以旧updated_at条件更新；原配置摘要只能预检，不能单独防止读后写窗口。对未推进时间的外部writer，需要在可验证的传输范围内将所保护的旧配置值纳入同一个PATCH条件；做不到就明确只提供有限并发检测，不能声称完全防止覆盖。摘要仅请求元数据，不新增列。配置PATCH严格只提交dirty配置字段及服务端新updated_at，禁止回写旧completed_items/cycle_no。不能用客户端传来的任意updated_at作为新版本。冲突409、保留草稿。

查询延用GET `/api/strategies`，补服务端分页以免未来任意增长；卡片加载仅取必要数据。无需新增统计RPC；当前小型JSON可从该页记录求数量，但记录目标达到容量上限时按需取详情，避免为了两行卡片读取所有账号画像。

删除确认说明只删除配置，不证明取消任何外部任务；接入runner后若真实运行中须按已核验停止机制处理，不能靠删除配置假装停止进程。

## H. 脚本触发与执行反馈

### H1. 已有能力清单

- `run-pipeline.mjs`处理本地JSON；可显式读数据库规则，不是策略驱动采集器。
- `run-wxrank-snapshot.mjs`处理已有快照；不能把“处理快照”叫实时采集。
- `run-tophub.mjs`抓取/重处理TopHub；普通merge与snapshot replace已存在。
- `wxrank-client.mjs`现有账号接口能力不能推断为公众号文章/date/month/keyword/wx_type五类采集能力。
- Edge Function ACTIVE v2有缺表依赖，不能直接认定可调用。

因此本包要求先核验复用入口，再决定启用哪些触发动作。五页配置不依赖runner完成；“完整采集闭环”验收则依赖真实runner，不得假通过。

### H2. 仅在合约满足时接入薄适配器

对每个候选入口记录：函数/脚本路径，输入来源，必需凭据名称，参数白名单，是否消耗外部配额，是否写远端，取消能力，输出schema，失败码。字段映射不能猜。用户未授权新增采集器时只包装已存在入口，不补建另一套采集业务。

可用本机service内的适配器暴露 `runAccountUpdate` 等动作，名称以真实能力为准。服务器固定调用函数或固定脚本+参数数组；绝不接受浏览器传入任意shell、可执行文件、目录或密钥。限制一次同类执行，重复提交返回同一运行或409；默认一次显式操作不自动循环。

若需HTTP异步状态，可新增 `/api/executions` 和 `/api/executions/:id` 作为应用API，运行元数据存在受控内存/现有报告文件，不能新建数据库jobs表；明确服务重启后内存状态未知，不承诺恢复。只有已启动真实进程才返回running，只有退出码及业务终态、必要读回都成功才返回succeeded。stdout必须脱敏，禁止直接传所有进程环境。

执行状态可用 queued/running/succeeded/failed/partial/unknown，但这是应用DTO，不是表中字段。没有真实排队系统时不显示queued；没有真实取消实现时不显示取消按钮；进度未知时显示已处理数量/当前阶段，不编百分比。

能力不可用时显示“执行器未接入/凭据未就绪”，禁用触发并给出明确原因。不要用setTimeout模拟完成，不要保存策略后自动跳到“成功”。

## I. 本机服务与错误边界

继续使用Host/Origin校验、JSON写请求、1MB请求上限和x-management-token。`/api/session`返回的writable仅表明本机会话令牌存在；写按钮可用还需真实数据库readiness，二者不能互相替代。现有服务允许HOST环境覆盖，要防止把本机令牌方案误部署公网；本次交付明确只接受loopback。

修复health：service须提供ping并调用底层真实只读查询 `accounts select account_id limit 1 count=false`，缺配置为not_configured，请求失败为error，成功才ready。测试注入一个没有ping的对象不应证明生产DB健康；测试应注入可观察且会失败的ping。

没有权限/数据库未配置时显示可理解的空态，禁止展示伪造示例账号。读数据失败保留旧数据并标注未刷新，不把错误当0条。404详情说明记录已被其他操作删除；409给“重新加载并保留草稿”的选择，不能自动覆盖。

安全转义、链接协议和字段白名单属于当前有数据写入管理工具的必要边界；不扩展到新的多租户/RBAC系统。若要公网使用，必须另立真实认证授权设计，不能改HOST就交付。

## J. 性能目标与证据

以下是待测目标，不是已经实现的成绩：同一设备和网络、真实只读数据、每场景至少20次，记录缓存命中/未命中分别的P50/P95。

| 项目 | 目标与测法 |
|---|---|
| 首屏依赖 | 当前页1次列表API；session/health独立；summary延迟，不阻塞 |
| 搜索 | 连续输入只在停止400ms后发最终查询；相同in-flight只发一次 |
| 行数 | 账号/文章响应最多pageSize，不含明细全量数组 |
| 请求大小 | 50条典型列表未压缩JSON优先<=200KB；超出先找多余字段，不删必需列凑指标 |
| 时延 | 未缓存列表API P95目标<=1500ms；网络不可控时报告实际值和影响，不虚构通过 |
| 本地渲染 | 收到50行响应到稳定绘制目标<=100ms；用性能标记/浏览器轨迹记录 |
| 写后刷新 | 最多刷新受影响的当前列表/详情；禁止额外五页查询或六表重数 |
| 万级规模 | 深页与组合筛选实测；数据库没搜索索引时不能保证毫秒级包含搜索 |

现有索引以btree为主，没有查询计划等证据时不要宣称 `%keyword%` 一定命中索引。慢查询只能先减少投影/计数、稳定排序、限制查询；需要新索引则作为超出“不改结构”约束的建议，不能自行执行。虚拟列表不是默认要求，100行分页没有证据无需引入。

### K3. JSON例子（仅用于测试和接口说明）

下面ID与文本是虚构fixture，不可据此请求生产写入；真实UI使用刚读取的ID和原值。`expected_*`均为API请求元数据，不能进入数据库列。

账号仅改标签：

```json
{
  "manual_tags": ["重点观察", "本地资讯"],
  "expected_manual_tags": null
}
```

账号仅改状态：

```json
{
  "decision_status": 1,
  "expected_decision": {
    "decision_status": 0,
    "decision_source": "auto",
    "filter_rule_id": null
  }
}
```

批量改状态的目标请求：

```json
{
  "ids": [101, 102],
  "decision_status": 2,
  "expected_decisions": [
    {"id":101,"decision_status":0,"decision_source":"auto","filter_rule_id":null},
    {"id":102,"decision_status":1,"decision_source":"manual","filter_rule_id":null}
  ]
}
```

每个ids必须恰好对应一份快照，重复/遗漏/额外快照拒绝。部分结果例子：

```json
{
  "count": 1,
  "requestedCount": 2,
  "succeededIds": [101],
  "failed": [{"id":102,"code":"CONFLICT","message":"该记录已变更，请重新加载"}]
}
```

新文本规则与数值规则的规范数据库载荷：

```json
[
  {"scope":"account","field_name":"name","operator":"contains","value_text":"示例关键词","value_number":null,"enabled":true,"remark":null},
  {"scope":"article","field_name":"comment_count","operator":"lt","value_text":null,"value_number":10,"enabled":true,"remark":null}
]
```

这个数组展示两个独立POST的载荷，现有POST /api/rules仍只接受单个JSON对象。不要误把示例数组整体发给原接口。

规则组保存建议请求结构：

```text
{
  group: {scope, field_name, operator},
  original_rows: [{id, scope, field_name, operator, value_text, value_number, enabled, remark, updated_at}],
  draft: {entries: [{id?, value, enabled, remark}]}
}
```

已有entry必须携带原id；新增entry省略id。服务端diff只允许修改original_rows范围，删除只来自原ID，新增使用identity；hit_count/created_at不接受草稿写入。groupKey与字段字典集中生成，不能在客户端和服务端各写一套不同键规则。

热词预览 `{ids,target_id}`，预览响应包含当前选中快照与服务端computed result；最终merge发送同一ids/target_id及expected_snapshots。不要用页面当前排序隐式表达目标。

### K4. 共享类型与文件拆分

项目是JavaScript，不为写类型迁移TypeScript。先用现有ESM常量和JSDoc定义 `PageQuery`、`PagedResult<T>`、`AccountListItem`、`AccountDetail`、`RuleGroupDraft`、`MutationResult`；确有多个文件复用再提到一个小型共享模块。DB row、UI item、PATCH input必须分开，严禁 `update(table,filter,{...form,...row})`。

必要时提取纯共享字段/运算符字典，使浏览器和server可分别导入不含凭据的常量；不能把含server-only client的模块打包给浏览器。每个业务操作只保留一个权威校验/转换入口，客户端轻校验用于交互，服务器校验决定是否写入。
