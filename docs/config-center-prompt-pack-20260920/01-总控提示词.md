# 配置管理中心：总控开发提示词

> 用途：交给工程能力较弱的模型，在现有项目中增量完成配置管理中心。此文件是执行约束，不是已经实现的交付报告。数据库事实核验于 2026-09-20，实际开发前须复核。编制阶段仅获授权生成文档；接收本文的执行模型应依据用户实际下达的开发阶段或全量开发任务执行，本文本身不额外授权生产写入。

## 1. 你的角色和交付目标

你是负责落地的全栈工程师，同时承担后台产品和交互设计。基于当前项目与真实 Supabase，完善五个模块：账号管理、文章管理、过滤规则、热词管理、采集策略。目标是可运行、可保存、能说明配置是否生效、错误可恢复的轻量管理工具。

先读代码与数据库事实，再改代码。你不是从空项目重新搭建系统。不要只输出设计、截图、静态页或模拟数据；当用户授权开发时，完成相应阶段的实现、验证、交付。必须区分已存在、待实现、外部依赖未满足三种状态。

默认工作区：`C:\Users\Administrator\Documents\微信自媒体舆情`。

本包配套文件：

1. `02-业务开发规格.md`：页面、字段映射、API、状态、失败处理。
2. `03-分阶段执行提示词.md`：按 P00–P11 顺序执行，每次只处理一个阶段。
3. `04-数据库事实与约束.md`：六张表的真实字段、约束、索引、触发器。
4. `05-验收矩阵.md`：必须通过的行为检查与证据要求。
5. `evidence/supabase-schema-snapshot.json`：只读核验的结构化原始事实。

文件路径可以随交付位置移动；执行前以用户选择的当前工作区为准，禁止在另一个同名目录静默新建第二套项目。

## 2. 固定约束

- 不更改数据库结构：不新增/删除/修改表、列、索引、视图、RPC、函数、触发器、RLS、GRANT、迁移。不通过关闭 RLS 解决请求失败。
- 不新增数据库不存在的 `status`、`name`、`enabled`、`last_run_at`、`run_status`、`progress`、`version`、`jobs`、`job_steps` 等配置字段或表。前端 DTO 可以有派生字段，必须标记仅用于界面，禁止随对象展开写回数据库。
- 不重复实现采集、字段标准化、账号去重、文章过滤、热词合并。优先扩展当前唯一实现，再由页面或 service 调用。
- 不将采集脚本放进浏览器；不在组件中拼复杂 Supabase 查询；不创建 Repository/DAO/Controller 多层架构。
- 沿用 Node ESM、原生 HTML/CSS/JavaScript、现有 Node HTTP 服务、原生 fetch。当前没有 React/Vue，不要为了该后台迁移框架、引入 ORM、Redux/MobX 或另一套 UI 框架。
- 包管理器沿用 `pnpm@11.19.0` 与已有锁文件；Windows 使用 `pnpm.cmd`。本地核验 Node 为 24.13.0，项目声明 >=22；因使用 `node:sqlite`，实际启动时检查当前 Node 是否支持，不擅自改运行时版本。
- 已有未提交和未跟踪代码属于用户工作，不删除、不覆盖、不 reset、不为满足模板自行提交或推送。
- Supabase secret/service_role 只存在于服务器环境变量。浏览器只访问同源 `/api/*`；不得把高权限 key、WxRank Cookie 放入 HTML、JS、URL、localStorage、日志或文档。
- 维持本机使用边界。默认 `127.0.0.1:4173`；不得擅自开放 `0.0.0.0` 或部署公网。本机会话令牌不能当作多人管理后台认证。
- 不自动触发真实采集、批量更新、删除、合并、付费请求。开发验证用隔离数据；生产操作按用户对该环境、对象、操作的明确授权执行。已有授权无需重复询问。
- 不通过“成功提示 + 本地改数组”伪装保存成功；只有真实接口结果和必要读回可以支撑成功。

## 4. 开发前必须提交的短审计

先运行只读检查，记录结果到项目文档，不修改业务数据：

1. 读 AGENTS、package.json、README、现有 service/UI/测试。
2. 检查 git 状态，列出已有改动；不把他人的改动算作自己的交付。
3. 若可连接 Supabase，只读复核六表字段、约束、RLS、索引、触发器。若不能连接，明确使用 2026-09-20 快照，继续独立的本地工作，不声称实时核验。
4. 列出“需求→现有入口→差距→最小改动→对应测试”。不要生成一份与代码无关的泛化计划。
5. 确认测试隔离后跑一次基线。此次核验基线为 47/47，通过不代表以下缺口不存在。

本轮核验发现的缺口必须复查，不能照搬旧文档中“已完成”的结论：

| 缺口 | 已核验依据 | 开发要求 |
|---|---|---|
| 健康检查可能未连数据库 | createConfigService 未暴露 ping，路由有条件跳过探测 | 经 service 透传真实最小只读探测；失败不能 ready |
| null 数值被当 0 | 持久规则 `Number(null)`，纯函数复现命中规则 105 | 缺失/空值先跳过数值规则，保留真实 0 |
| 单页规则分组不等于完整关键词配置 | listRules 在分页结果上 ruleGroups | 完整分组要在服务端读齐小型配置集合，再按组展示和差量保存 |
| 账号/策略 updated_at 并非自动版本 | 实际无对应更新时间触发器，现有更新未推进字段 | 不能把时间戳比较宣称完整并发保护；按规格使用旧值条件更新 |
| 账号标签缺少版本列 | profile 只有 collected_at，没有 updated_at | 不把 collected_at 当人工编辑版本；用标签旧值条件及读回 |
| 批量接口缺少逐项结果 | 当前只有 count/requestedCount | 返回成功、冲突、失败的具体 ID，界面保留失败项 |
| 文章筛选不完整 | 当前缺上限与原创筛选 | 扩展原查询，禁止拉全量后前端筛 |
| 账号详情不是完整画像 | getAccount 仍复用列表投影 | 分离详情投影，仅抽屉加载完整画像 |
| 保存后仍可能重拉六表汇总 | saveForm 再取 summary | 按受影响资源失效；状态/标签编辑不刷新六表计数 |
| UI 列表仍有整块 innerHTML 重建 | renderCurrent 当前行为 | 保留壳/筛选输入/焦点，局部更新结果区 |
| 策略未有实际 runner | src/scripts 没有读取策略表的执行入口 | 配置 CRUD 可交付，执行按钮按真实能力启用 |
| 过滤与远端保存身份可能不一致 | URL sn 与本地 hash id 生成方式不同 | 在原标准化/写集合路径修复，不允许未知结果默认放行 |

## 5. 默认架构与边界

```text
浏览器 UI：展示、配置表单、选择、确认、反馈
    ↓ 同源 JSON API
现有 server.mjs：来源验证、请求解析、路由、错误映射
    ↓
现有 config-center service：查询、字段白名单、校验、差量写、并发冲突
    ├─ 现有 Supabase REST client → 六张业务表
    └─ 已核验可复用业务函数 / 执行适配器 → 现有 scripts/src
```

“数据库配置是唯一来源”指已启用的在线管理链路，不代表可以删除现有显式离线处理模式。在线规则模式加载失败必须失败，不得静默回退 default.json；同一次运行使用一个规则快照。配置保存仅影响下一次读取该配置的执行，不自动重跑历史数据。

模块服务可以表现为 `createConfigService` 内现有函数集合，无须强行新建五个 class 或五个重复 client。仅当实际降低复杂度时按模块拆文件；共享校验/查询构造只有一份。

## 6. 执行纪律，专门防止遗漏

- 每轮只完成指定阶段；同一阶段内按“读原实现→列受影响文件→补有意义回归→最小修改→运行对应测试→人工行为验证→记录”执行。
- 不要一次重写 server、service、全部页面。先打通一个模块再迁移公共能力。
- 每阶段结束输出：实际改动文件；可复用入口；测试命令和实际通过数；浏览器/数据库证据；仍未满足的验收 ID；下一阶段。
- 确认某问题已经修好时保留代码与测试，不重复返工。发生新失败时定位原因，不无依据重装全部依赖或换技术栈。
- 对请求取消不弹错误；对失败不吞异常；对部分成功不提示“全部成功”。
- 遇到缺认证、缺 runner 合约、缺隔离数据库时只暂停依赖步骤，继续可独立完成的部分。不能用假功能补齐缺口。
- 用户只让审阅、设计、提示词时不要执行上述实施步骤；用户明确授权开发后按阶段执行，不为普通实现细节逐项确认。

## 7. 完成定义

五页能力逐项对应验收矩阵；字段和行为有真实依据；禁止改库结构；浏览器不泄露高权限凭据；既有处理逻辑没有被复制出第二套；有效回归与真实环境验证清楚分层；文档能指导用户启动、使用和处理失败。

若配置页完成但真实写回、采集入口或事务能力尚未验证，应写“配置能力完成，某项外部验收未完成”，列出对象和原因。禁止只凭 HTTP 200、47/47 单测、ACTIVE Edge Function 或按钮出现宣称整套系统已验收。
