# 配置管理中心开发提示词包

已按附件需求、当前仓库和 Supabase 真实结构整理，覆盖6表86字段、12个开发阶段、112项验收。适合工程能力偏弱的模型逐阶段执行，避免一次生成大批互相不兼容的代码。

**本轮交付的是提示词与核验依据，没有修改系统代码或数据库，没有执行真实采集、业务保存、删除或合并。**

## 推荐用法

1. 让执行模型先读取 `01-总控提示词.md`、`04-数据库事实与约束.md`，并读取当前仓库代码。
2. 先发送 `stages/P00.md`，建立代码与数据库基线。
3. 依次发送 `stages/P01.md` 至 `stages/P11.md`。每阶段都读取02对应规格及K接口清单、05相关验收ID。
4. 同一个会话保持上下文；新会话重新提供01、04和前一阶段交付记录，避免靠模型猜已完成内容。
5. 已明确授权整个开发时可以让模型自动连续执行阶段；如果希望控制弱模型的改动量，则逐次只授权一个阶段。阶段划分不要求你重复批准已授权的普通实现细节。

不要只把五页UI需求交给模型。数据库字段、旧代码缺口、脚本能力边界和失败验收同样属于开发输入。

如果使用平台只允许一个提示词文件，可使用 **`完整版-可直接复制.md`**。该文件由五份正文按总控→数据库→业务→阶段→验收顺序拼接，内容较长；上下文较小的模型优先使用分阶段方式，不要截断后半段验收要求。

## 已明确的重要事实

- 原项目已有 Node 原生服务和原生 JS 管理中心，应增量完善，不默认新建 React/Vue 工程。
- 6张业务表均开启RLS；当前public没有行策略，浏览器不能被假设为可直接CRUD；沿用server-only访问。
- articles有每账号保留最近20条的INSERT触发器，不是历史全量文章仓库。
- filter_rules使用name/verification/read_count等逻辑字段，不能替换为wx_name/verify/read_num列名。
- account/strategy的updated_at没有UPDATE触发器；hotwords无版本列；补偿写不能包装成事务。
- 策略cursor是配置请求页数，0未激活；不存在页面可调用的完整策略runner。date/month targets编码无真实依据时不编造。
- 现存账号同步Edge Function依赖当前不存在的jobs/job_steps；ACTIVE不证明可用。
- 当前47/47测试通过，但已复现null规则、判定身份和health探测的缺口，提示词已要求具体回归。
